# 2026-09-24 — Babyz Pizza revenue app

## Built
Single-page revenue/order tracker for the Babyz Pizza cloud kitchen (Garia, Kolkata).
Files: `index.html`, `assets/styles.css`, `assets/app.js`, `vendor/chart.umd.min.js` (Chart.js 4.4.4, vendored),
`data/babyz-data.js` (repo copy), `server.js` (zero-dep local writer), `start-local.bat`, `README.md`, `.gitignore`.

## Key architecture decisions
- **Data file format is JS, not JSON**: `window.BABYZ_DATA = {...}`. Reason: a `<script src="data/babyz-data.js">`
  tag works over `file://`, whereas `fetch()` of a JSON file is blocked by CORS on `file://`. This lets the
  desktop-opened page still show real data.
- **Three runtime modes**, detected in `boot()`:
  - `server` — local context AND `http://127.0.0.1:8787/api/health` reachable → full read/write.
  - `draft` — local context, no writer → localStorage only, warning banner.
  - `live` — hosted (e.g. GitHub Pages) → read-only; `body.is-live` hides every `.readonly-hide` element.
- **Two data files, always written together** by `POST /api/save`:
  - desktop: `C:\Users\soumi\Desktop\Babyz Pizza Data\babyz-data.js`
  - repo: `<repo>/data/babyz-data.js`  ← the one that gets committed/pushed
- `server.js` sends `Access-Control-Allow-Origin: *`, so even a `file://` page can POST to it.
- Swiggy weeks = Sunday→Saturday, first week of a month starts on the 1st (`weeksInMonth()` in app.js).
  Sep 2026 → W1 1–5, W2 6–12, W3 13–19, W4 20–26, W5 27–30.

7. Date-wise charts regenerate from the data on load, so new dates create new axis points and weeks.

## Final three-file model
| file | path | role |
|---|---|---|
| MAIN | `<Desktop>\Babyz Pizza Data\babyz-data.js` | the real local copy |
| STAGE | `<Desktop>\Babyz Pizza Data\babyz-data-pending.js` | 2nd local copy — deletions land here |
| REPO | `<repo>\data\babyz-data.js` | read by the site; the file you commit |

- add    → MAIN + STAGE + REPO
- delete → STAGE only (`state.pending` array + `meta.pendingDeletes` in the STAGE file)
- undo   → STAGE rebuilt from MAIN
- confirm→ STAGE pushed into MAIN + REPO, pending cleared

`state.base` = authoritative data (no deletions applied); `state.data` = view (base minus pending).
`applyPending()` runs at boot so staged deletions survive a reload.

## Server API (server.js)
`GET /api/health` · `GET /api/state` (reads REPO) · `POST /api/rows` (add) · `POST /api/stage` (delete)
· `POST /api/undo` · `POST /api/confirm`

## Bug found and fixed
`.modal-backdrop { display: flex }` overrode the `[hidden]` attribute's UA `display:none`, so the popup
rendered permanently. Fixed with a global `[hidden] { display: none !important; }` in styles.css.
**Lesson: a CSS `display` declaration on an element that is toggled with the `hidden` attribute always
wins. Also: assert real visibility with `getClientRects().length`, not `el.hidden` — the property is
true even when the element is still painted.**

## Week algebra (assets/app.js, after `weekLabel()`)

var WEEK_FIRST_END = '2026-09-05';   // the one short first window
var WEEK_LEN       = 7;

daysBetween(a, b)         // inclusive
payoutWeekDays(startISO)
payoutRange(p)            // {start: p.weekStart, end: p.weekEnd || payoutWeekEnd(...)}

# 2026-09-24 (even later) — every Swiggy weekly view now follows the payout weeks

## Request
"If any swiggy data based graph uses the weekly data, update it to use as per the new weekly
logic added and it must auto populate weeks when added for n number of rows."

## Audit result — two places were still on the old hardcoded model
1. **`renderMoneyCharts()` / `mnChannelChart`** (Money tab) bucketed by `allWeeks()` and matched
   payouts with `x.weekStart === w.start`, so a custom or merged payout week landed nowhere.
2. **`swiggyRows()`** attached `week` via `weekOf(s.date)` (Sunday→Saturday calendar), which fed
   the **"Swiggy week" badge** in the Swiggy master table.

`swWeekChart` and `swDeductChart` were already correct (driven by `payoutRows()`).

## New week model (assets/app.js)
- `gridWeekOf(iso)` — the 7-day grid anchored at 1 Sep 2026: 1–5 Sep (short), then 6–12, 13–19,
  20–26, 27 Sep–3 Oct, … Returns null before 1 Sep 2026.
- `weekPeriods()` — one **contiguous, sorted** list of weeks:
  1. recorded payout ranges first (authoritative, includes merged);
  2. every dated record not covered falls back to `gridWeekOf`, or to `weekOf` (calendar week)
     for dates before 1 Sep 2026, **clipped at 31 Aug** so it can't swallow the 1–5 Sep week;
  3. empty weeks are kept so a quiet week is an empty slot, not a gap;
  4. overlapping segments are merged, and a payout segment wins the `source` label.
- `swiggyRows()` now resolves `week`/`weekStart`/`weekEnd` from `weekPeriods()` and adds
  `weekSource` (`'payout'` | `'grid'`).
- `shortRangeLabel()` — `rangeLabel` minus the year, for crowded chart axes. Exposed as
  `axisLabel` on `payoutRows()`; full range stays in the table badge and moves into the chart
  tooltip **title** callback.
- `payoutRows()` gains `axisLabel`; `allWeeks()` was **deleted** (dead once the money chart moved).
- The comment block above `weeksInMonth()` was rewritten to say calendar weeks are now only a
  fallback (offline weekly chart + pre-1-Sep dates), not the Swiggy week definition.

## UX decisions worth remembering
- Swiggy table badge: **orange (`badge warn`)** when the order sits in a *recorded* payout week,
  **grey (`badge muted`)** when the week is only derived from the grid, `—` for pre-1-Sep dates.
  A `title` attribute explains which.
- `swDeductChart` now plots **only weeks with `gross > 0`**. A week with a payout but no recorded
  orders used to plot 0 % deduction, which reads as "no commission" — actively misleading. It now
  shows the empty-state message instead.
- Offline weekly chart deliberately left on Sunday→Saturday calendar weeks: offline has no payout
  cycle to follow.

## Gotcha hit
`baseOpts(extra)` does a **shallow** `Object.assign`, so passing `plugins: {...}` **replaces** the
whole default plugins object and silently drops the default legend styling. Always re-declare
`legend` when you override `plugins`. (Same for `scales`.)

## THE BUG THAT MATTERED (caught by the probe, invisible in the UI)
Menus live in **two** objects: `state.base` (what `writeAll()` posts → written to the files) and
`state.data` (what the page renders). `addRow()` writes both, but my first pass mutated only
`state.data`. Result: the screen updated perfectly — new item in the list, in the dropdown, group
count went 5→6 — while **`/api/rows` kept writing the old menus**, so nothing was ever persisted.
`renderAll()` only runs on `res.ok`, so the UI looked healthy.

**Fix:** `menuApply(mutate)` runs the mutation against `state.base.menus` *and* `state.data.menus`,
and every op pushes a **fresh object per copy** so base and data never share a reference.

**Lesson: when an app keeps a "file copy" and a "view copy" of the same state, every mutation must
go through one helper that touches both. A UI-only assertion cannot catch a missed write — assert
the persisted state through the API/files as well.**

## Category propagation (menu = source of truth)
`resolveCategory(channel, item, stored)` looks the item up in `menuIndex()` and returns the menu's
category; only if the item is **not in the menu at all** (deleted) does it fall back to the
category stored on the order. Applied in `offlineRows()` and `swiggyRows()`. So moving an item
between groups re-colours its table badges and re-slices the doughnut, while deleting is
non-destructive to history. Verified no-op on the existing data (every order already matched its
menu group), so it only takes effect after an edit.

# 2026-09-24 (last) — write gate hardened: editing is local-only, period

## Request
"Addition/Deletion of any data and addition/deletion of any menu item should only be allowed in
local, not when hosted on github pages."

The hiding already worked, but an audit found **two real holes**.

## Hole 1 (critical) — the `?local=1` escape hatch
`isLocalContext()` returned true if the URL carried `?local=1`. So
`https://<user>.github.io/<repo>/?local=1` made a hosted page think it was local → mode fell to
`draft` (writer unreachable) → `is-live` never applied → **the add and delete controls came back**.
Fixed by deleting the switch. `isLocalContext()` is now a strict allowlist:
`file://`, `localhost`, `127.x.x.x` (any loopback), `0.0.0.0`, `::1`, `*.localhost`.

## Hole 2 — the writer trusted any website
`Access-Control-Allow-Origin: *` on every response meant any page the user had open could POST to
`http://127.0.0.1:8787/api/rows` while the writer was running. Now `cors(req, res)` checks
`req.headers.origin`: only `null` (a `file://` page) or a loopback origin gets headers; anything
else gets **403 on both the preflight and the request**. Because `application/json` POSTs trigger a
preflight, blocking the preflight is what actually stops the write.

## Refactor — one gate instead of ten checks
The 10 scattered `if (state.mode === 'live') { readOnlyWarn(); ... }` guards were replaced by:

```js
function canWrite() {
  return isLocalContext() && (state.mode === 'server' || state.mode === 'draft');
}
function guardWrite() { if (canWrite()) return true; readOnlyWarn(); return false; }
```
Every mutation is now `if (!guardWrite()) return;` (or `return Promise.resolve({ ok: false })`).
Evaluated **live**, not cached at boot. The read-only class comes from the same predicate —
`state.readOnly = !canWrite()` → `body.is-live` **and** `body.is-readonly` — so the controls are
hidden *by construction* rather than by a rule that can drift.

Also marked `readonly-hide`: the two revenue-settings inputs (only the Save button was hidden
before, so a hosted visitor could fiddle with dead controls) and `#pendingBar`.

## Note for future edits
`.readonly-hide` is now the **only** mechanism hiding editing controls, and it is driven by
`canWrite()`. Any new editing UI must carry `.readonly-hide` *and* call `guardWrite()` — the CSS
alone is cosmetic; the gate is the actual protection. `body.is-readonly` exists alongside
`body.is-live` so the two names can't drift apart.
