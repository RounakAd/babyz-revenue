# Multiple pizzas on one order (Swiggy + Offline, local only)

Request: *"Add option to add mutiple pizzas when saving an order or editing an order, both
for swiggy and offline when hosted on local."*

## The model decision — one row, many lines
An order is still **one row**. It gained an optional array:

```js
lines: [{ item: 'Og Margherita Pizza', qty: 2, price: 200 }, …]
```

The alternative (N rows sharing a date/customer) was rejected because the invoice is
per-order and **already had an `items: [...]` array** that `drawInvoice` loops over — the
architecture was clearly built for multi-line bills. One row also keeps "edit *an order*"
meaningful and the table tidy.

**Backward compatibility is total.** `rowLines(row, kind)` returns `row.lines` when present
and otherwise builds a single line from the old flat fields, so the 29 orders already on disk
(no `lines` anywhere) read exactly as before — no migration, and the table shows no stacked
list and no "varies" for them.

## The trap that shaped the implementation
The flat fields (`item`, `qty`, `sellingPrice`/`rate`) are kept on the row as a **summary** —
`qty` becomes the *total units* across lines and `sellingPrice` the *first line's* price. That
means `sellingPrice × qty` is **no longer the order's value** for a multi-pizza row, and any
consumer still doing that multiplication would produce a silently wrong number.

So every money figure is derived through the lines, and the complete set of price×qty
products was enumerated and fixed (grep `sellingPrice` / `\.rate\b`):
`describeRow` (offline + swiggy), `offlineRows`, `swiggyRows`, `invoiceModel`.
`offlineRows`/`swiggyRows` are where `amount`/`gross`/`final`/`cost` are computed, and every
KPI, chart and table reads those — so fixing those two functions fixed the whole app at once.

**Rule for the future: never multiply `row.qty` by `row.sellingPrice`/`row.rate` again.**

## What else had to become line-aware
* `pass()` — item/category filters match if **any** line matches (`row.lineItems` /
  `row.lineCats`), and the search haystack joins all line items.
* **Item charts** — `byItem[l.item] += l.qty` per line, not `byItem[r.item] += r.qty`.
* **Category doughnuts** — attributed **per line**, which is what makes a mixed veg/non-veg
  order land in both slices. The offline offer is per *order*, so it is spread across lines
  **in proportion to their value**; the doughnut total still equals the sum of the orders'
  `final` amounts exactly as before.
* **Table Item cell** — stacked list when >1 line (`itemsCell`); `priceCell` prints
  **varies** when the lines disagree, since one price column can't honestly show several.
* **Invoice** — one `items[]` entry per pizza; row pitch tightens past 6 lines
  (`many` branch) and the existing footer-push guard covers the rest.

## The UI
One reusable repeater drives both add panels **and** the ✏️ Items modal:
`renderLinesEditor` / `wireLinesEditor` / `readLinesEditor` all take the same `.lines-editor`
root, so the panel and the modal cannot drift. Rows are delegated off `.lines-body`, so
lines added later are covered without re-wiring. `readLinesEditor` stops at the first bad row
and names it ("Pizza 2: enter a price of 0 or more"); the same pizza at the same price is
**merged** into one line.

`✏️ Items` lives in `actionsCell()` (both channels) and reuses the `requestXEdit` /
`applyXEdit` shape: fresh object per state copy, `writeAll()`, ✅ popup, and a no-op guard
that reports "Nothing changed" instead of rewriting the files.

`itemSelectHtml` re-adds an **off-menu item** as its own option, otherwise merely opening the
editor on an order whose item was deleted would silently change what was sold.

## Two bugs found and fixed on the way
1. **`modalOk.disabled` leaked between popups.** `openModal` never reset it, so cancelling
   the order-no editor while its confirm was disabled left **every later popup** with a dead
   confirm button. Fixed by resetting it in `openModal`.
2. **The add-panel dropdowns were built once** (`dataset.ready`), so an item added in the
   Menus tab never appeared in them without a reload. `renderFilters` now rebuilds them when
   `JSON.stringify(state.data.menus)` changes, carrying a half-typed order across via
   `snapshotLines()` (a non-validating read).

# Row controls → pencils in the cell; invoice date = order date

Request: *"add a pencil icon button beside the options that are currently allowed to be
edited rather than adding entire buttons, it is making each row longer. Also, all invoices
should show invoice generated date as the date of order."*

## 1. Edit controls are now pencils inside the cell they edit
The Actions column had grown to 4-5 text buttons per row (Invoice, ✏️ Items, ✏️ Order no.,
✏️ Customer, Delete) and rows were stretching. Confirmed with Rounak: pencil goes **in the
cell it edits**, not icon-only in Actions.

* `pencil(attrs, title)` → icon-only `<button class="pencil readonly-hide">✏️</button>`
  with `title` + `aria-label`. `cellEdit(value, pencil)` wraps both in `.cell-edit` (flex).
* New cell builders `customerCell()`, `orderNoCell()`, `itemCell()`, used by
  `renderSwiggyTable()` **and** `renderOfflineTable()`.
* `actionsCell()` is now **Invoice + Delete only**. *(Supersedes the "✏️ Items lives in
  `actionsCell()`" note above.)*
* Investments keep their pencil in the Actions column — that editor changes three adjacent
  columns (Qty/Rate/Amount) at once, so there is no single cell to sit beside.
* CSS: `.cell-edit`, `.pencil` (opacity .5, hover reveals). Pencils are `readonly-hide` and
  every handler still calls `guardWrite()`.

**Measured in a real browser (Edge/CDP, 1500px viewport), Swiggy table:**

| | before | after |
|---|---|---|
| Actions cell width | 461px | **173px** |
| Actions buttons | 5 | 2 |
| table width | 1711px | **1487px** |

Net **-224px** per row. The offline table (13 cols) now fits its container exactly (1416px).

**Still open (offered, not done):** `.wrap` caps at `max-width:1500px` (24px padding) so the
table container is 1416px, but the Swiggy table's min-content is 1487px → it overflows by
**71px at any window size** and Delete sits at the end of that scroll. Pre-existing (was
295px). The residual floor is `thead th { white-space: nowrap }` plus long item names.
Needs a design call: wrap the two-word headers, trim `th` padding, or icon-ise Invoice.

## 2. Invoice generated date is the ORDER's date
`invStamp()` was `new Date()` + clock time — i.e. whenever you opened the invoice. Now
`invStamp(row.date)` → `'Generated ' + dNice(date)`, e.g. `Generated 14 Aug 2026`.
**The clock time is deliberately dropped**: an order records a date but never a time, so
today's time beside the order's date was misleading. Reuses `dNice()` so the stamp reads
exactly like the invoice's own `Date` field.

## Harness gotchas (new this session)
* jsdom ships **no `fetch`** and **no `ResizeObserver`** — both needed for boot.
* Chart.js needs a `canvas` back-reference on the 2D context or it throws
  "can't acquire context from the given item".
* **The invoice only draws after the logo resolves.** `withInvoiceLogo()` waits on
  `assets/logo.js` (which sets `window.BABYZ_LOGO`) and then `new Image().onload`. jsdom loads
  neither, so `openInvoice()` hangs and **no canvas text is ever captured**. Inject
  `assets/logo.js` as a script and stub `window.Image` to fire `onload` on the next tick.
* Canvas recorders are cached on the canvas element — reset by clearing each recorder's own
  `_texts` array. Clearing the registry silently stops collection after the first render.
* The app hardcodes `API_BASE = http://127.0.0.1:8787`, so a test server on another port makes
  the page fall back to **draft** mode (still editable, different banner). Use 8787 for a
  faithful capture.

# Closing the 71px Swiggy-table overflow (the "do all changes suggested" follow-up)

The overflow flagged above is now **fixed and measured**. Two CSS changes in `assets/styles.css`:

* `thead th` — `padding: 10px 12px` → `10px 9px`, and **`white-space: nowrap` → `normal`**.
* `tbody td` / `tfoot td` — `padding` → `9px` horizontally. `tbody td` keeps `nowrap`.

Rationale: every data cell is `nowrap` on purpose, so the **header labels also** contribute to the
table's minimum width. Letting two-word headers wrap to two lines buys width back for ~16px of
header height.

**Correction (found by the negative test below).** An earlier draft of this note — and of the CSS
comment — claimed the header labels were setting the minimum width "all by themselves". They were
not. Reverting each half in isolation shows the 71px was **66px of horizontal padding** (12px → 9px)
plus **39px of header labels**; the headers alone are worth 39px, the padding alone 66px, and
*neither alone was sufficient*. The CSS comment now states this correctly.

**Measured in a real browser (Edge/CDP, 1500px viewport; container is 1416px):**

| | before | after |
|---|---|---|
| Swiggy table width | 1487px | **1416px** |
| Swiggy overflow | **+71px** | **0px** |
| Swiggy min-content | 1487px | **1382px → 34px headroom** |
| Offline overflow | 0px | 0px (min-content 1209px → 207px headroom) |
| header row height | 37px | 53px (two lines for the two-word labels) |
| Actions cell | 173px | **167px** |
| Offline Actions cell | — | 190px |

34px of headroom is the important number: the fix is not knife-edge, so it will not re-break on a
machine with slightly wider font metrics. Screenshots confirm the wrapped headers and Invoice +
Delete fully visible with no horizontal scroll.

## Re-checked while the browser was up

  `readonly-hide`, each beside its own value. `actionsCell` = Invoice + Delete only.
* **Read-only gate still sound.** With `body.is-live.is-readonly` forced on: **0 of 33 pencils**,
  **0 of 13 delete buttons**, **0 of 2 add panels** on screen, while all **11 invoices** stay
  (they only read). 0 JS errors.

## New harness gotchas (both cost real time)
* **`getComputedStyle(el).display` is the wrong visibility test in a real browser.** A child of a
  `display:none` parent still reports its own display, so it counted 2 delete buttons as "visible"
  on a hosted origin and looked like a leak. `getClientRects().length > 0` is the correct test.
  (jsdom is the mirror image: there `getClientRects()` is 0 for visible inline elements, so use
  `display` there. Neither method works in both.)
* **`return` + newline in an injected expression silently yields `undefined`.** `return ${expr};`
  where the expression starts on the next line triggers ASI → `return;` → `undefined`, with a clean
  `{"type":"undefined"}` and **no `exceptionDetails`**, which reads exactly like "the page has no
  data". Wrap it in `JSON.stringify(...)` inside the page instead — it also survives values that
  `returnByValue` mangles.
* `Page.captureScreenshot`'s `clip` is in **page** coordinates, not viewport ones. After
  `scrollIntoView`, adding `window.scrollY` is easy to get wrong; a plain viewport shot after
  scrolling is more reliable for a sticky-header table.

## `BABYZ_DESKTOP_DIR` does not redirect the repo copy
`REPO_FILE = path.join(__dirname, 'data', MAIN_NAME)` — always the real repo, whatever
`BABYZ_DESKTOP_DIR` says. So a sandboxed server still **writes the committed data file** on every
save. This bit during verification: a save at 13:26 left an uncommitted change in
`data/babyz-data.js` (investment `inv55`, Bread 1→2 / ₹50→₹100) that took a while to attribute,
because the Desktop master was untouched and the sandbox looked like the only thing written.
Rounak then committed it himself in `10e9446 "edit changes"` — so it was his edit, and reverting
would have destroyed it. **Lesson: when a sandbox server is running, `data/babyz-data.js` is live —
check `git diff` on it before and after, and never assume a Desktop override isolates the repo.**
The follow-up sweep was therefore run from a **throwaway clone** of the repo (`cp server.js
index.html assets vendor data` into a temp dir) so `REPO_FILE` resolved to the copy. That is the
right way to sandbox this app; the `BABYZ_DESKTOP_DIR` env var alone is not enough.

# Editable week ending on the Swiggy payout form

Request: *"allow adding a date for week ending — which might not be 7 days from week start date. if
no date is given and only start date is given, consider week end date as the 7th date, for ex if
start date is on a monday, default end date should be on that week Sunday. But date change should
also be allowed for the end date."*

## The data model already supported it — only the UI did not
`payoutRange(p)` has always been `{ start: p.weekStart, end: p.weekEnd || payoutWeekEnd(start) }`, and
`payoutRows()`, `weekPeriods()`, the merge logic and the `· Nd` in the table all read through it. So
an explicit `weekEnd` was already honoured everywhere. The work was therefore **UI + validation only**
— the read path needed no change at all. Worth checking this first on similar requests: it turned a
"feature" into a form change.

## The default rule, and the one exception that must not move
`payoutWeekEnd(start)` = **start + 6**, which is exactly the user's example (Monday start → that
week's Sunday). Confirmed against the real data: the two recorded weeks are 6–12 Sep and 13–19 Sep,
both Sun→Sat, and `start + 6` reproduces them precisely.

The exception is `2026-09-01 → 2026-09-05` (the documented short first week, 5 days). This is the one
place the default is *not* the 7th date, so it was left alone and flagged to Rounak: `gridWeekOf()`
walks the entire 7-day grid off that value, so changing it would re-bucket every order in the app.
The user can now simply override the ending in the form if they want 1–7 Sep.

## `dataset.auto` — the "don't clobber what the user chose" flag
`updatePayoutEnd()` stores the last value *it* wrote in `endInp.dataset.auto`. A start-date change
re-fills the ending **only while the field still equals that remembered value**:

* untouched ending → follows the start day (7th day);
* user-chosen ending → survives a later start change, and is flagged red if it now precedes the start;
* cleared field → re-fills the default.

This is the same shape as the investment editor's `amountTyped` flag, deliberately — one pattern for
"the user has taken control of this field" across the app. `endInp.min = start` blocks the picker
from offering earlier days, and submit refuses with *"The week ending cannot be before the week start."*

## Layout gotcha: the day count had to go in the LABEL
`.add-grid` is `align-items: end`, so anything taller than an input inside a `.field` breaks the
row's alignment (the taller cell's bottom aligns with the others and its input floats up). The live
day count therefore lives in the `<label>`, not under the input.

The first screenshot showed the note rendering as **"WEEK ENDING 7 DAYS"** — labels are
`text-transform: uppercase`, so the note read as part of the label. Fixed with `text-transform: none`
on `.field-note`. Only visible by looking at it; the DOM assertion passed either way.

## Verification
15 functional checks driving the real form (default for Mon 7 Sep → Sun 13 Sep; Sun 6 Sep → Sat 12 Sep;
the 1 Sep exception; a custom ending honoured; **a custom ending surviving a later start change**;
clearing re-filling the default; an ending before the start flagged *and* writing nothing; a 4-day
week saved to the file with its own `weekEnd`; the table showing `5 Oct – 8 Oct 2026 · 4d`; the form
resetting; no page errors) — **all 15 passed**.

Those assertions were then folded into the `babyz-app-verify` harness so they are permanent rather
than thrown away, taking it from 10 checks to **21, all passing**. The harness now contains exactly
one write test — adding a payout to read the custom `weekEnd` back out of the data file. That is safe
only because it writes to the clone; the final check re-hashes the real repo file and would fail
loudly if it moved.

README updated in three places: the "Swiggy payout weeks" section (the ending is editable, with the
rules above), the note that payouts have no row editor, and the payout-table description.
