# 2026-09-27 — the EPERM save failure: diagnosis, recovery, hardening

## The report
User screenshot: `Save failed: EPERM: operation not permitted, rename
'C:\Users\soumi\Desktop\Babyz Pizza Data\babyz-data.js.tmp' -> '...\babyz-data.js'`

## What actually caused it (earlier "read-only attribute" theory was WRONG)
`writeAtomic` in `server.js` did `writeFileSync(tmp)` then `renameSync(tmp, file)`.
On Windows, `rename` over an existing file needs **DELETE** access on the target.
Something had the file open *sharing read+write but not delete*, so the rename was
refused — while a plain write to the same file still worked.

Proof, run in the real data folder (self-restoring probes):
| probe | result |
|---|---|
| rename -> a **new** name in the same folder | OK |
| rename -> the **real** `babyz-data.js` | **FAIL EPERM** |
| `copyFileSync` over `babyz-data.js` | OK |
| `writeFileSync` over `babyz-data.js` | OK |
| `[System.IO.File]::Open(..., FileShare::None)` | **FAILED — "being used by another process"** |
| `Get-Item -Force` | `Attributes: Archive`, `IsReadOnly: False` |

**Not the read-only attribute.** Not the CLI's `NODE_OPTIONS` brokered-fs shim
either — the probe fails identically with `NODE_OPTIONS` cleared.

**The holder, named by the Windows Restart Manager API:**
```
pid=13880  app=Zed
```
Zed (the editor) had `babyz-data.js` open. The lock is **intermittent** — Zed holds
it while watching/scanning, so saves fail sometimes and succeed other times.

## Recovery — 7 stranded orders, all back
The interrupted save left `babyz-data.js.tmp` (27,037 B) beside a stale
`babyz-data.js` (24,809 B). Deep-compared the two: the orphan was a **pure
superset** of MAIN — byte-identical everywhere except **7 extra offline orders**,
all `2026-09-26`, all Chicken Pepperoni Pizza ₹180, ids `off_mujcw5og041y`,
`off_mujcwa9hm4sd`, `off_mujcwef7m0vi`, `off_mujcwvpq8rvz`, `off_mujcwzbwfx9n`,
`off_mujcxh54vca7`, `off_mujcymlfa0wf`.

Promoted the orphan into MAIN + REPO with a fresh `updatedAt`.
- offline **17 → 24**, revenue **₹3,180 → ₹4,440** (the 7 add ₹1,260)
- MAIN and REPO now byte-identical, 27,037 B each, orphan `.tmp` gone
- swiggy 10 / payouts 2 / investments 59 unchanged; menus unchanged
- MAIN and REPO were *already* content-identical before recovery (only `updatedAt`
  differed, 09-24 vs 09-25) — so there was no real "repo one edit ahead" divergence
- Backups: `%TEMP%\babyz_recover_104351\` (MAIN.js, ORPHAN_TMP.js, REPO.js,
  MAIN_pre_recovery_*.js, REPO_pre_recovery_*.js)

## The fix
`server.js` `writeAtomic` now:
1. writes the `.tmp` as before;
2. tries `renameSync` up to 6× with backoff, `chmod 0o666` on both files between
   attempts (clears a real read-only bit, harmless otherwise);
3. **if rename is still refused, falls back to `writeFileSync(file, text)`** — a
   plain write only needs WRITE access, which the lock allows — then removes the
   `.tmp`. Logs `[write] rename blocked (EPERM) — wrote … in place instead.`
4. only if *that* also fails does it throw, with a message naming the file, the
   code, and the likely holders.

**Verified end-to-end** in an isolated sandbox (`BABYZ_PORT=8799`,
`BABYZ_DESKTOP_DIR=<temp>`), holding a Zed-style lock (`FileShare::ReadWrite` =
deny delete) via PowerShell:
- lock check: `LOCKED — rename refused with EPERM`
- `POST /api/rows` -> **HTTP 200**, desk orders 24→25, repo 25, **no orphan `.tmp`**
- server stderr showed the fallback line

## The fix, client side
A failed write used to be a 3.6 s toast that was easy to miss. Added
`saveFailed(what, res)` in `assets/app.js`, used by `writeAll` / `writeStage` /
`doUndo` / `doConfirm`. It opens the existing modal (which stays until dismissed)
with the raw error, plus a hint that keys off `EPERM|EACCES|EBUSY` (file held /
read-only) vs `Failed to fetch` (writer not running). `openModal` gained
`hideCancel`; `.modal p code` added to `styles.css` so long Windows paths wrap.

## Left for the user
- The local writer was **not running** at the end of this session (nothing listening
  on 8787) — re-run `start-local.bat` to pick up the fixed code.
- Zed still holds the Desktop data file; closing the file/workspace in Zed removes
  the cause entirely.

## Follow-up, same session: the user restarted the server and pruned the recovery
While wrapping up, a server reappeared on 8787 — **PID 18168, started 10:58:47**,
which is *after* `server.js` was last edited (10:54), so **the running server already
has the fixed `writeAtomic`**. No restart needed.

The live files had meanwhile moved from my recovered **24 orders / ₹4,440** to
**19 / ₹3,540**, MAIN and REPO byte-identical, `updatedAt 2026-09-27T05:29:43Z`,
and `babyz-data-pending.js` present with `pendingDeletes: []`.

The two rows still present for `2026-09-26` carry **my recovered ids**
(`off_mujcw5og041y`, `off_mujcxh54vca7` — both `Mithai`), not fresh `uid()`s. So the
page did receive the recovery, and the change is a **confirmed deletion** (staged
`pendingDeletes` non-empty during the delete, `[]` after `/api/confirm`) of the 5
`Walk-in` rows — the user's own curation, not a clobber. **Do not re-apply the
recovery**; it would re-add rows the user deliberately removed.

Worth knowing: **the app has no conflict detection.** `writeAll` posts `state.base`
wholesale, so any save from a tab holding older data silently overwrites newer
on-disk data. That is exactly the shape of the near-loss here.

Backups kept at `%TEMP%\babyz_recover_104351\` — `ORPHAN_TMP.js` still holds all 24
orders including the 5 `Walk-in` rows:
`off_mujcwa9hm4sd`, `off_mujcwef7m0vi`, `off_mujcwvpq8rvz`, `off_mujcwzbwfx9n`,
`off_mujcymlfa0wf`.

# Per-row editing of investment qty / rate / amount (local only)

Request: *"Allow option to edit investment amount, quantity and rate when hosted on
local for each row."*

## What was added
`renderInvTable()` has its **own** action cell — it does **not** go through
`actionsCell()`, which is only used by the Swiggy and Offline tables. So the new button
went straight into that cell:

```js
'<button class="btn btn-ghost btn-sm readonly-hide" data-edit-investment="' + esc(r.id) +
  '" title="…">✏️ Edit</button>'
```

New pair in `assets/app.js`, modelled on `requestCustomerEdit` / `applyCustomerName`:
* `requestInvestmentEdit(id)` — popup with `#invEditQty`, `#invEditRate`,
  `#invEditAmount`.
* `applyInvestmentEdit(id, before)` — mutates `state.base` **and** `state.data`
  (fresh object per copy), then `writeAll(...)`, then the ✅ confirmation popup.
* Delegated on `document` in `wireEvents()`:
  `[data-edit-investment]` → `requestInvestmentEdit(ei.dataset.editInvestment)`.
* CSS: `.modal-form-row` (3-col grid) + `.modal-hint` in `assets/styles.css`.

## The amount rule (the interesting decision)
First cut recomputed `amount = qty × rate` on **every** qty/rate input. The browser test
caught that this **silently discards a hand-typed amount**: typing 999.99 then touching
qty replaced it with 136.5, and 136.5 is what got saved. Unacceptable — never silently
throw away what the user typed.

Final rule: `amountTyped` flips true the moment the amount field is edited; from then on
qty/rate changes leave the amount alone. `.modal-hint` always states the relationship —
`Amount follows qty × rate…`, or `Amount differs from qty × rate (₹X) — it will be saved
exactly as typed.` So a custom amount survives and the divergence is visible.

`#modalOk` is disabled until all three fields hold finite, non-negative numbers.

## Verified in a real browser (isolated sandbox on 8799, real data never touched)
| step | result |
|---|---|
| 59 Edit buttons, visible on localhost | ✅ |
| modal prefilled `qty 1 / rate 1600 / amount 1600` | ✅ |
| type amount 1500 → change qty to 2 | amount **stays 1500**, hint `differs from ₹3,200` |
| change rate to 100 | amount **stays 1500**, hint `differs from ₹200` |
| set amount 200 (= 2×100) | hint flips to `Amount follows qty × rate` |
| save custom `2 / 100 / 250` | **file, STAGE and table all `2 / 100 / 250`** — custom amount kept |
| confirm popup | `Qty 1 → 2 \| Rate ₹1,600 → ₹100 \| Amount ₹1,600 → ₹250` |
| hosted origin `babyz-hosted.test` | **0 of 59 buttons visible**, `body.is-live.is-readonly`, forced `.click()` opened no popup, file unchanged |
| JS errors | **0** |

Note the sandbox trick that made this safe: the test copy's `API_PORT` was patched
8787 → 8799 with `sed`, so the test page could never reach the user's live writer.

## Follow-up worth doing
Swiggy weekly payouts are still not editable (no customer/qty/rate). If a payout amount
needs correcting, the user has to edit the source data — worth offering a payout editor
next.

# Per-row Swiggy order number — add / edit `#XXXX` (local only)

Request: *"add option in each swiggy order row to add an order number and edit that
order number when hosted on local, it will be of format `#XXXX` where XXXX can be any
4 digit number."*

## Format rule (tightened)
`normalizeOrderNo` was loose (`[A-Za-z0-9-]`, 1–20 chars). It is now **exactly** the
requested shape — one rule for both the add panel and the row editor:

```js
function normalizeOrderNo(raw) {
  var s = String(raw == null ? '' : raw).trim().replace(/\s+/g, '');
  if (s.charAt(0) === '#') s = s.slice(1);
  if (!s) return { ok: true, value: '' };        /* optional — blank removes it */
  if (!/^\d{4}$/.test(s)) return { ok: false, value: s };
  return { ok: true, value: s };
}
```

* `1234` and `#1234` both accepted; **stored without the hash** (`orderNo: "1234"`).
* `12`, `123`, `12345`, `abc`, `#12` → rejected. `#0042` is fine (it *is* 4 digits).
* Blank is valid and clears the field.
* The `#` is a **display** concern only, added at the four places that show it: the table
  cell (`'#' + esc(r.orderNo)`), the search haystack, `invoiceRef` (`'#' + typed`), and
  the invoice's `Order no.` line. Safe to do now because **no existing row carried an
  `orderNo`** — nothing in the data needed migrating.

## The editor
`actionsCell(collection, id)` gained a **Swiggy-only** button (Offline rows correctly get
none — `collection === 'swiggyOrders'` guard):

```js
'<button class="btn btn-ghost btn-sm readonly-hide" data-edit-order-no="' + esc(id) + '" …>✏️ Order no.</button>'
```

New pair `requestOrderNoEdit(id)` / `applyOrderNo(id, before)`, same shape as every other
row editor (open popup → validate → mutate `state.base` **and** `state.data` with a fresh
object per copy → `writeAll` → ✅ popup). Title is *Add* when the row has no number and
*Edit* when it does; confirm text `Add number` / `Save number`; a `.modal-hint` states the
`#XXXX` rule and that blank removes it; `#modalOk` is disabled while the input is invalid;
Enter saves; the field is focused and selected on open. Delegated on `document` in
`wireEvents()` via `[data-edit-order-no]`. `index.html`'s `#swOrderNoAdd` was given
`inputmode="numeric" maxlength="5"` and placeholder `e.g. #1234`.
